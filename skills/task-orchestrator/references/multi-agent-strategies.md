# 多方案竞选与多 Agent 分工

本文件描述可选工作方法，不是宿主原生的 `/arena`、`/swarm` 命令。先确认工具、权限、预算和可用模型；没有并行工具时可顺序提出方案并验证，但必须标明不是独立 Agent 执行。

## 方案竞选：同一问题，多种解法

触发：T2/T3 的重要设计或架构有真正不同的可行方案，选错代价高，且能低成本做对比。已确定的局部改动跳过。

1. 固定同一份要求、约束、预算、输入版本与可观察验收标准。
2. 让 2–3 位独立执行者分别提出不同方案，优先生成可运行/可渲染的小样；不得把改措辞当作不同设计。
3. 统一比较功能正确性、用户体验、资源成本、维护性、风险与实测证据。
4. 选择主方案，只合并兼容的优势，然后重新验证整合后的实际产物。
5. 保存方案取舍和反证；多个模型意见一致仍不等于功能通过测试。

## 分工：不同问题，不同责任人

触发：任务依赖已稳定、分工界面明确、写入不冲突、具备委派权限且协调收益为正。

- 分工前明确每人的目标、负责文件、禁止改动范围、输入版本、交付接口和验证条件。
- 同一文件、时间轴、分支或共享状态不能在无隔离情况下并发写入；使用独立工作区和唯一整合者，或改为串行。
- 主执行者处理冲突、实际运行/渲染验证、审查发现和最终交付；子 Agent 的文字自报不是验收。
- 对抗式审查要求另一审查者尽可能从原始需求和产物着手，提供可复现证据；记录审查者及覆盖范围。

例：视频先固定分镜和时间轴，分别制作画面与声音，最终由单点整合和声画实测；共享时间轴不能任由多个 Agent 并写。
