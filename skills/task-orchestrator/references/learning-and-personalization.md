# 纠错、复盘与专属模式

工作方法分别借鉴 `correct`、`reflect`、`automate-me`，并非保证宿主存在同名命令、会自动记忆或能读取过去的聊天。

## 纠错：反复出现的同类问题

触发：同类错误再次出现，或已有一次高后果故障暴露系统性缺陷。

1. 收集复现步骤、版本、日志与实际产物，区分证实根因和猜测。
2. 找最早的错误源头；同一修复思路失败两次，先质疑共同前提。
3. 按作用范围选择最小的可执行保障：架构/数据约束优先，其次类型/Schema、静态检查或 CI、自动回归测试，文档提醒最后。
4. 能运行时证明旧行为会失败、新实现通过，检查相关回归与误报。
5. 权限不足时仅提出候选修复；不得自动修改共享全局规则、破坏用户配置或虚构验证结果。

## 复盘：成功的方法形成候选 Skill

触发：已验收的复杂任务完成，或有重大返工/新方法值得复用。记录触发条件、所需工具、步骤、验收证据、失败信号、反例和边界。

优先最小修改现有 Skill；必须新增时先建立候选 `SKILL.md`，用一项正例和一项不应触发的反例检查。共享之前需要维护者审阅、必要回归和回退路径；跨项目证据充分才上升至 Core。

## 专属模式：按证据学习工作方式

触发：用户明确要求，或存在稳定的多次工作模式且获授权归纳。只用真实可访问的历史和反馈，不编造过去的任务、工具结果或偏好。

把稳定的流程、验收标准、成本预算、模型偏好、授权边界、交付风格分别记录；剔除一次性例外、敏感数据和与宿主规则冲突的偏好。

产出独立的个人模式候选，用来路由现有 Skills，不复制整份 Core；至少用两项历史任务与一个反例测试，取得用户审核后保存到适合的私有位置。没有历史读取能力时明确说明，不能冒充已归纳。

## 诚实降级

没有子 Agent、模型调用、脚本执行或产物访问能力时，清楚标记仅完成方法设计或静态检查，不能宣称“已经自动纠错”“已做独立审查”或“实际可用”。
