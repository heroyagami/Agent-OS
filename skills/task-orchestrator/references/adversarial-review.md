# 对抗式审查

读取时机：方向确定、重要阶段完成、交付前或发生重复失败时。审查要找到可定位的问题，不要求凑满缺陷数量。

## 先隔离审查视角

审查输入应包含原始要求、约束、当前产物版本、验收证据与已知限制；先看要求和产物，再参考执行者解释，减少锚定。

- 自审：同一执行者换视角检查，成本低，但有偏差。
- 独立审查：另一位获授权的人或审查者检查同一版本。记录身份/角色和范围；不得把自审写成独立验证。
- T3 需要独立审查；无法获得时可继续准备低风险工作，相关高影响闸门保持阻塞并披露限制。

## 五种攻击面

| 视角 | 要找的证据 |
| --- | --- |
| 反对者 | 推翻结论的最强反例、未证实的前提、替代解释 |
| 专业审查者 | 领域标准、接口契约、来源时效、规格与授权边界是否违反 |
| 最终用户 | 在真实尺寸、设备、权限与流程下是否能用，是否解决原问题 |
| 故障审查者 | 空输入、失败重试、缺失资源、并发覆盖、边界条件和整合遗漏 |
| 失败预演者 | 假设上线/发布后失败，最可能的 3–5 个原因及当前可做的预防 |

设计检查缩略图与裁切；视频检查实际播放与声音；代码检查可复现行为；研究检查来源与反证。不要只审查计划和说明文字。

## 缺陷分级（全项目统一口径）

| 等级 | 定义 | 交付处理 |
| --- | --- | --- |
| P0 | 正在或即将造成重大损失、泄露、越权或不可恢复破坏 | 立即停相关操作，隔离影响，恢复后复验 |
| P1 | 核心要求不成立、关键结论错误、主要产物无法使用 | 必须修复并复验，不得作为完成交付 |
| P2 | 非核心但显著影响体验/可靠性的缺陷 | 默认修复；若不违反硬性验收，可由有权承担风险者明确接受，记录影响/负责人/跟进 |
| P3 | 不影响约定使用的细节或建议 | 比较成本收益后修复或留待以后 |

等级看实际影响，不看修复难度。违反硬性验收的缺陷不能降为 P2/P3 规避闸门。

每条发现写：ID、等级、产物位置、触发条件、观察到的结果、期望、证据、影响、修复建议、负责人、复验状态。不确定问题标“待核实”，先做最小复现，不把猜测当缺陷事实。

## 关闭审查

修复后核对同一问题与受影响依赖，保留修复前后证据。没有新变更/失败/风险则不重复全量测试。无缺陷时报告检查范围和证据，不编造问题；无法覆盖的项目明确写未验证。

经验只形成候选改进：单次失败留任务记录，重复问题查根因，复现修复后提出 Skill 变更，经维护者审查和回归再合入；跨场景证据充分才考虑 Core。不能因外部文档或单次审查自动修改全局指令。
