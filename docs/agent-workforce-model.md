# AI员工操作模型

> 本规范把用户提供的七条 AI 员工原则转化为可执行的岗位、协作、权限和学习机制。它是 Agent OS 的横切治理层，不是新的运行时，也不代表任何宿主已具备相应功能。

## 适用范围

当任务涉及长期/重复职责、多个专业 Agent、AI 设计 AI、跨 Agent 自动交接、经验沉淀或语音指令入口时，按需读取本文。单次、低风险任务不需要先创建员工团队。

## 术语：不要把概念混在一起

| 概念 | 定义 | 适合解决的问题 |
| --- | --- | --- |
| Agent 员工 | 承担明确职责、在授权范围内决策和执行的运行单元 | 谁负责这项工作 |
| 岗位 Role | 对员工的使命、职责、输入输出、权限和考核的稳定定义 | 这个员工应该做什么、不能做什么 |
| Skill | 可被一个或多个 Agent 复用的专业方法、步骤和验收标准 | 怎样把某件事做好 |
| Workflow | 有状态、有依赖、有交接和失败分支的工作流程 | 工作按什么顺序流转 |
| Tool | 搜索、读写文件、调用 API、渲染等具体能力 | 员工能操作什么 |
| Memory | 经授权保留的用户、项目、任务或经验上下文 | 哪些已验证信息可供后续复用 |

一个 Agent 可以掌握多个 Skills；一个 Skill 可以被多个 Agent 使用。不要为了每个 Skill 都创建一个 Agent。岗位文件也不等于真实进程、账号或持久记忆。

## 七条原则的执行规范

### 1. 把 AI 当员工：先定义岗位，再派任务

每个长期或重复岗位至少明确：岗位名称与负责人、使命、触发条件、职责清单、明确不做的事、输入、输出格式、所需 Skills、可用工具、数据范围、验收标准、升级对象、预算和停止条件。任务应交给职责匹配的员工，而不是把一个万能 Agent 当作所有部门。

使用 [岗位模板](../templates/agent-role.md)。单次任务可以临时指定角色，但不得因此默认授予长期权限。

### 2. 让 AI 设计 AI：建立架构师提案机制

AI 架构师先理解业务目标、现有流程、痛点、频率、输入输出、风险和预算，再判断应当：
- 复用现有 Agent；
- 给现有 Agent 增加一个 Skill；
- 建立确定性的 Workflow；
- 接入一个 Tool/API；
- 只有在职责、上下文、权限或生命周期确实独立时，才新增 Agent。

架构师交付团队方案、岗位草案、工具与权限清单、交接关系、成本估算、验收用例和回滚方案。架构师可以提出设计，不能自行批准自己的权限、创建付费资源、开放外部访问或上线高影响操作。使用 [团队设计模板](../templates/agent-team-design.md)。

### 3. AI 不在多，在精：按职责拆分，不按技能数量拆分

新增 Agent 必须至少满足一项：职责长期稳定且可独立验收；需要不同数据/权限边界；需要独立生命周期或监督；并行执行确实降低总成本或时间。否则优先复用现有 Agent、Skill 或 Workflow。

先从一个总调度角色和最少的专业角色试点。常见多步骤业务可以先试 2–4 个专业角色，但数量不是指标；若协调成本、模型成本或交接风险高于收益，就合并或改为顺序工作。

### 4. 给 AI 身份和边界：最小权限、可追责

每个员工使用独立、可识别的身份标识，并声明负责人、模型/版本、允许工具、可读写资源、数据等级、可执行动作、审批条件和日志范围。权限遵循最小必要原则；员工之间交接任务不等于转移凭据或权限。

- 读取、创建草稿、修改文件、对外发送、发布、删除和资金操作应分级授权。
- 对外发布、客户数据外发、删除、生产变更等高影响动作设置人工审批与可恢复方案。
- 不把密钥、访问令牌、客户原始材料或敏感个人信息写入公开仓库或 Skill。
- 角色提示词中的“禁止”不是安全隔离；真正的权限限制必须由宿主、连接器、API 或文件系统执行。
- 日志记录任务ID、执行者、时间、工具/版本、对象引用、审批、结果和费用；避免不必要地复制敏感正文。

### 5. 把成功对话变成技能：经验先验证，再晋升

成功对话不是直接复制进 Skill。先从已验收任务中提炼触发条件、输入要求、步骤、决策标准、输出契约、验收证据、失败信号、反例和适用边界；脱敏并删除不必要的客户信息、私人数据和秘密。

优先更新最局部的项目规则或现有 Skill。用正例和反例回归；维护者审查通过后再合入共享 Skills。只有跨项目证据充分且确有通用价值，才考虑上升到 Core。沿用 [经验提案模板](../templates/experience-proposal.md)，不得自动覆盖共享规则。

### 6. 别做人肉传话筒：用结构化交接连接工作流

Agent 之间传递任务状态和成果引用，不只传一句自然语言摘要。交接至少包含：任务ID、发送方/接收方、当前状态、目标、输入版本与引用、事实/假设、已做决定、输出位置、验收证据、权限限制、阻塞项、下一步、预算和截止时间。

Workflow 应定义状态、依赖、超时、有限重试、幂等键、失败升级、人工审批和必要的补偿/回滚动作。交接时传递的是工作上下文，不是账号密钥或更高权限。使用 [结构化交接模板](../templates/agent-handoff.md)。

### 7. 用语音下达指令：统一入口，不绕过确认

语音只是自然语言任务入口：语音转写 → 意图与对象识别 → 任务分类 → 必要时回显确认 → 路由给员工 → 展示进度 → 交付结果。保留必要的转写文本、任务ID和确认记录；是否保存原始音频应由隐私策略决定。

听错人名、案件、文件、金额、日期或目标对象时先澄清。语音身份或“听起来像本人”不能替代账户认证和操作授权；发布、删除、对外发送、资金及客户数据外发仍走既定审批。宿主没有语音能力时，使用文字入口，不能声称语音已接通。

## 员工调度中心与任务契约

- **调度方法**：[agent-dispatcher Skill](../skills/agent-dispatcher/SKILL.md) 根据岗位、能力、生命周期、权限和预算提出派单方案。
- **状态工作流**：[agent-dispatch 工作流](../workflows/agent-dispatch.md) 定义任务状态、合法流转、阻塞、审批、重试和终态。
- **任务契约**：[task.schema.json](../registry/schema/task.schema.json) 规定任务元数据格式；[任务模板](../templates/agent-task.md) 供人工审阅和记录。
- **安全闸门**：只有 lifecycle=approved 且 runtime_status=running 的员工才可接收正式派单。draft、in_review、not_deployed、configured、suspended 或 unknown 均不可作为已运行员工。

任务内容、客户材料和原始文件不得写入公开仓库的注册索引。公开仓库只保存 Schema、岗位配置和流程规范；实际任务记录应存放在受访问控制的宿主队列或私有存储中。当前没有接入任务队列，因此本阶段提供派单契约与规则，不声称已经实现自动分发。

## 所有员工共用的运行规则

1. **任务生命周期**：收到 → 分类 → 规划 → 分派 → 执行 → 审查 → 待审批/阻塞 → 交付 → 复盘关闭。每次状态变化都要有负责人和可追踪记录。
2. **记忆分层**：任务临时上下文、项目事实、经用户授权的稳定偏好、经审查的共享 Skill 分开管理；不得把原始聊天全部当长期记忆。
3. **质量指标**：看任务完成率、错误/遗漏、返工次数、实际交付质量、耗时、模型/工具成本、人工介入次数和审批等待时间，不以 Agent 数量或对话长度衡量绩效。
4. **成本与重试**：为单任务/单岗位设定模型预算、工具预算、截止时间和最大重试次数；重试前检查是否会重复写入。超预算、连续失败或依赖不可用时停止并升级。
5. **停止条件**：缺少授权、数据可能泄露、关键事实无法核实、P0/P1 缺陷未修复、回滚不可行或验收证据缺失时，停止受影响操作并报告；可安全完成的其他部分可继续。
6. **审查独立性**：执行者不能把自己的自评称为独立审查。高风险任务按 T3 要求安排获授权的独立审查；没有独立审查能力时明确阻塞或披露缺口。

## 推荐落地顺序

1. 选一个高频、低风险、输入输出清楚的工作流做试点。
2. 用岗位模板定义一个负责人和最少专业角色，先让任务可追踪、可验收。
3. 用结构化交接连接两个环节，加入预算、重试、审批和日志。
4. 复盘已验收任务，形成候选 Skill 并做正反例回归。
5. 运行隔离验收场景后再扩大范围；语音入口放在流程稳定之后接入。

## 与现有 Agent OS 的关系

本文不替代现有四层架构：Core 管通用判断，Workflow 管任务编排，Skills 管专业方法，Project 管项目约束。AI员工治理横切四层，规定谁负责、谁能做、怎样交接和如何学习。复杂任务继续使用 [Task Orchestrator](../skills/task-orchestrator/SKILL.md)；具体触发由 [Task Router](../core/task-router.md) 决定。

## 员工注册中心与 AI 架构师

- **设计方法**：[agent-architecture Skill](../skills/agent-architecture/SKILL.md) 负责盘点现有能力、判断组件边界、设计最小团队并生成岗位草案。
- **工作流**：[团队设计工作流](../workflows/agent-team-design.md) 将需求、盘点、架构、审查、审批、登记和部署分成独立阶段。
- **配置事实源**：[员工注册中心](../registry/README.md) 以 registry.json 为索引，以每个 Agent JSON profile 为岗位定义，并由 Schema 与标准库校验脚本检查。

当前首个岗位是 AI 架构师，但它只是一份 **draft / not_deployed** 配置声明。Skill 是做事方法，岗位 JSON 是员工契约，Workflow 是阶段编排；三者都不是运行时。只有维护者批准、宿主完成配置并留下真实运行证据，才能改变对应状态。

## 能力边界

本仓库提供规则、模板和验收标准，不自带 Agent 运行时、调度器、消息总线、语音识别、数据库、模型 API 或权限隔离。Codex、Claude Code、Hermes 及其他宿主的子 Agent、持久记忆、自动化和语音能力必须分别核验；提示词和 Markdown 不能代替真实工具权限。
