# Agent Architecture

## 使命

把业务目标转化为最小、可治理、可验收的 AI 员工方案。先复用现有能力，再决定是否新增 Agent；输出设计与配置草案，不把文档伪装成运行中的员工。

## 触发条件

- 用户要求设计 AI 团队、AI 员工、岗位或 Agent 组织。
- 需要新增、合并、拆分、停用 Agent，或评估团队成本与权限。
- 重复工作已形成稳定流程，需要判断 Skill、Workflow、Tool 或 Agent 的边界。

简单单次任务不触发，不为了使用本 Skill 而创建团队。

## 设计步骤

1. **盘点**：读取员工注册中心、现有岗位、Skills、Workflows、Tools 和项目规则；确认是否已有可复用组件。
2. **定义目标**：明确业务目标、触发频率、输入、输出、时限、质量标准、数据等级、预算和不可执行事项。缺少关键条件时只问最必要的问题。
3. **做架构决策**：依次比较复用现有 Agent、增加 Skill、编排 Workflow、接入 Tool/API、创建新 Agent。说明选择理由及被否决选项。
4. **最小拆分**：每个 Agent 必须有独立、稳定、可验收的责任，或真实独立的数据/权限边界；否则合并。避免为每个 Skill 建一个 Agent。
5. **定义岗位**：填写使命、职责、不做事项、输入输出、Skills、工具白名单、数据范围、审批、升级、预算、停止条件和验收指标。
6. **设计协作**：明确任务状态、交接字段、依赖、并行边界、幂等键、失败升级和回滚。
7. **对抗审查**：检查重复岗位、过度拆分、越权路径、敏感数据暴露、成本失控和无法验证的承诺。
8. **生成提案**：使用 [团队设计模板](../../templates/agent-team-design.md)，输出岗位卡、交接图、权限矩阵、预算假设和验收用例。
9. **登记草案**：按 [注册中心规范](../../registry/README.md) 生成 JSON 草案并运行校验；未经维护者批准，不改变正式注册状态。
10. **交付**：清楚区分已设计、已登记、已批准、已配置、已运行；没有宿主证据不得宣称已部署。

## 架构决策准则

| 需求特征 | 优先选择 |
| --- | --- |
| 可复用的固定方法 | Skill |
| 顺序明确、状态可预测的步骤 | Workflow |
| 搜索、文件、API、渲染等外部能力 | Tool |
| 独立、持续、可验收的责任 | Agent |
| 仅一次、低风险任务 | 直接执行，不新增组件 |

## 权限与安全闸门

- 默认只读现有项目资料；工具使用必须来自宿主实际提供的 allowlist。
- 架构师可以提出权限，但不能批准自己的权限、创建凭据、购买资源或自行部署。
- 对外发送、发布、删除、生产变更、客户数据外发和付费资源必须走明确审批。
- 客户材料、敏感个人信息、密钥和访问令牌不得写入公开注册中心或 Skill。
- 预算、负责人、审批人或回滚方案缺失时，保持 draft，不进入 configured/running。
- 运行状态必须有真实宿主配置与执行证据；Markdown、JSON 和提示词本身不是运行证据。

## 产出验收

提案应能回答：为什么需要这些岗位、为什么不能用现有组件、每个岗位做什么/不做什么、谁批准权限、如何交接、成本如何控制、失败如何停止、如何证明结果。关键问题没有答案时，标为待决或阻塞，不自行补造事实。
