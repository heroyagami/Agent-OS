# Software Engineering

## 先读取再修改

1. 读取仓库元数据、分支、工作区状态、范围内项目指令、相关实现与测试、构建/依赖声明；保留用户未提交工作和未知文件。
2. 把需求写成触发条件、当前/期望行为、接口与验收。修复先复现或建立可观察证据；无法复现时区分推测与事实。
3. 从业务结果推导最小架构，标出模块、数据、接口、错误行为与迁移依赖；沿用现有约定，不把技术偏好变成需求。

## 计划与实现

- 先验证最危险的假设：依赖 API、运行环境、数据兼容、性能或部署约束；使用隔离/非生产小样，检查版本与来源。
- 建立最小端到端实现，再补齐边界、权限与错误路径；MVP 不能代替用户要求的完整行为。
- 接口/Schema 先稳定再并行；给各任务明确文件范围与契约，避免覆盖他人修改。没有收益时单 Agent 顺序执行。
- 采用范围最小的改动；不附带无关重构、依赖升级、格式化或全局配置变化。审阅生成文件与锁文件是否必要。
- 输入验证、访问控制、敏感信息、超时/重试与幂等按真实风险设计；不要在代码、日志或示例中写入真实凭证。

## 检查与发布

1. 针对改变的行为运行项目已有检查；对有实质回归风险的行为补充有意义测试。低影响文案变化不机械新增测试，无法运行则说明环境与待补动作。
2. 检查正常路径、相关边界和失败路径；集成/UI 改动验证实际运行结果，不能只凭类型检查或构建成功宣称功能正确。
3. 审查 diff：遗漏的调用方、兼容性、迁移/回退、错误处理、权限与性能瓶颈。修改后复验相关测试，避免无变化重复全量运行。
4. 生产变更升 T3：准备迁移顺序、备份/恢复验证、影响范围和独立审查，核对授权。禁止擅自清库、强推或覆盖用户工作。
5. 提交前确认目标仓库、分支与远端新变化，避免丢失并发提交；提交/部署后回读目标版本并检查实际行为。提交成功不等于部署成功。

## 交付与示例

交付说明包含改变的行为、关键文件/提交、实际执行的检查与结果、未验证项及风险。无法构建或缺环境时可交付变更，但不得标“已全面测试”。

例如修复重复下单：先复现重复请求 → 确认幂等契约及数据库约束 → 实现最小修复 → 验证正常/重复/并发/失败重试路径 → 审查迁移与既有调用方 → 交付证据；不要只在前端禁用按钮。
