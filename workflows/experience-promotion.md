# Experience Promotion 工作流

> 将已验收实践转化为候选知识，并通过隐私、证据、正反例和维护者审批闸门。工作流不会自行修改共享 Skill/Core。

## 状态

| 状态 | 含义 | 允许的下一步 |
| --- | --- | --- |
| candidate | 从已验收任务中提炼出候选方法 | redacted / rejected |
| redacted | 已完成隐私清理和来源核对 | in_review / rejected |
| in_review | 等待专业/维护者审查 | tested / rejected |
| tested | 正反例回归通过 | approved / rejected |
| approved | 有权维护者批准合入 | merged / deprecated |
| merged | 已按目标范围合入并回归 | deprecated |
| rejected | 未通过审查或测试 | 终态；需新证据才能另建提案 |
| deprecated | 已废弃或被更新规则替代 | 终态 |

状态不得跳过隐私审查、正反例测试或维护者审批。approved/merged 必须有审批人和时间；Core 范围必须有跨项目证据。

## 阶段

1. **来源核验**：确认任务已完成、结果已验收，存在可回读证据。只记录私有来源引用。
2. **模式提取**：说明问题、根因、适用条件、步骤、输出契约、失败信号和反例；区分事实与假设。
3. **范围选择**：Project 优先；可复用专业方法进入 Skill/reference；Core 仅接纳跨项目稳定原则。
4. **隐私审查**：移除客户名称、案号、原始文件内容、个人信息、凭据和无关细节。隐私审查未通过，不进入 in_review。
5. **正反例回归**：至少一个正例和一个反例。正例验证应该执行的路径；反例验证不适用时能够拒绝、澄清或停止。
6. **对抗审查**：查找过度泛化、冲突、权限扩张、成本增加和潜在副作用。
7. **维护者审批**：维护者审阅证据、目标范围、风险和回滚方案；提案作者不能自行批准自己的共享规则。
8. **局部合入**：只修改批准的目标文件，版本化提交并运行相应回归；不得顺带改动无关 Core 或其他 Skill。
9. **观察与回滚**：记录新规则在后续任务中的有效性、误触发和副作用；出现回归问题时按提交/版本回滚。

## 通过条件

- 来源是已验收任务或可复现修复，不是未证实的主观感受。
- 提案脱敏，无客户原文、秘密或不必要的个人信息。
- 至少一个正例和一个反例通过。
- 目标范围与证据强度匹配；Core 有跨项目证据。
- 维护者审批、合入提交和回滚方式可追踪。
- GitHub Actions 的结构检查通过；这不替代专业审查或实际使用观察。

## 私有数据边界

原始任务、案件材料、客户文件、音频、完整聊天和密钥留在受控私有系统。公开仓库只保存通用规则、脱敏提案元数据和测试摘要。不得把可反向识别客户的引用或文件路径公开。
